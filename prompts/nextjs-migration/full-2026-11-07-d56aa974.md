**SQLite or JSONL**

You chose JSONL earlier because it's readable and auditable. Moving fully to SQLite would give up part of that.

| | JSONL files | SQLite |
|---|---|---|
| Audit and Git | Every change shows in a diff, line by line | One binary file, so Git can't show what changed |
| Readability | Open in any editor | Needs a tool or a query to look inside |
| Queries | Read everything into memory and filter in code | Real queries, joins and indexes |
| Integrity | Nothing stops bad references or duplicates | Foreign keys and constraints |
| Concurrent writes | Risky if two processes write at once | Handled safely |
| Setup | Nothing to install | Built into Node 24 (`node:sqlite`), so no extra dependency, but still marked experimental |
| Fit with the data | Natural for append-only logs: source events, role changes, decisions | Natural for current state: positions, pipeline stages, check results |

At this size (3 positions, a few dozen events), JSONL is fast enough. SQLite's real gains are integrity and convenient queries, not speed.

**My recommendation: both, with clear roles.**
- **JSONL stays the source of truth.** Sources, role events, client decisions and recruiter check results are append-only, readable and visible in diffs. This is what you want to show auditors and in the presentation.
- **SQLite becomes a disposable index**, rebuilt from the JSONL by `pnpm harness rebuild` and kept out of Git. The UI and CLI query it for the pipeline, the version table and check history. If it breaks, delete it and rebuild.

This matches the story in readme.html: in production the log would live in a bucket and the index would be a real database. The MVP shows the same split in small. The cost is one extra rebuild step, plus making sure nobody writes to SQLite directly.

If you'd rather keep it simpler, pure JSONL with in-memory queries works fine at this size. You can add SQLite later without changing the files.
