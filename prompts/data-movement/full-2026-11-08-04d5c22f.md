There's no mock data on `main` yet: no `harness/` folder or data. What exists are the UI prototypes. So the names below follow the layout we agreed earlier (`harness/data/sources/` for raw messages, `harness/data/store/` for extracted knowledge). They aren't final.

## Two separate jobs
Your question mixes two things, and I'd keep them apart:

1. **Delivery** stands in for a real connector (Gmail, tl;dv, Slack). Something "arrives". In production, a webhook or a scheduled poll does this, not the AI.
2. **Ingestion** is the harness itself. It runs the rule-13 stages on whatever arrived: analyse what changed → questions → answers → recheck → human review → publish → recruiter recalibration.

Every option below changes only how delivery happens. Ingestion stays one shared path, so every option produces the same stage files.

## Options for delivery

**A. Scripted timeline + "new update" button (recommended)**
- Pre-written future messages wait in `harness/fixtures/<scenario>/timeline/`, for example `03-kickoff-transcript.md`, `05-email-budget-cut.md` and `06-news-expansion.md`. Each has an "expected reading" file: which fields should change, the severity, and the questions it should raise.
- The UI shows "1 new message from Northwind". Clicking it, or running `pnpm harness deliver next`, copies the next item into `harness/data/sources/<client>/<channel>/`, adds it to the manifest, and starts ingestion.
- **Benefit:** it's repeatable, the demo tells a story (v1 JD → v2 after kickoff → v3 after the expansion news), and every step can be checked against its expected reading.
- **Cost:** the same updates every time, so variety means writing more fixtures.

**B. AI-generated random update**
- A button asks the model to invent a plausible client change.
- **Benefit:** variety and a bit of surprise in a demo.
- **Cost:** no expected reading, so you can't check it. The same AI would be inventing and judging the change. It can also invent "client facts" you never approved, which is exactly what we told the agents not to do.

**C. Paste or forward**
- "Add client update": the recruiter pastes an email or transcript, picks the channel and date, and it's saved as a source file.
- **Benefit:** this is how recruiters actually work (forwarding emails), and evaluators can test their own input.
- **Cost:** none of these inputs come with an expected reading.

**D. Folder watcher**
- Drop any file into `harness/data/inbox/` and the server detects it.
- **Benefit:** the closest copy of a real connector.
- **Cost:** it's invisible to a non-technical user and does nothing that A doesn't.

## My recommendation
Build **A** as the main path, plus **C** as a secondary "add your own update" for testing. If you want **B** later, label it "generated". Save each generated message as a file first, so it goes through the same visible path and can be audited.

On "the AI calls a script with a prompt": I'd keep the prompts inside the ingestion stages, not in delivery. The AI shouldn't decide when news arrives. It should react to it the same way, every time, stage by stage.
