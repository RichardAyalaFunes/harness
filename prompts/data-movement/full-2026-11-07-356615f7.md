No mock data is on `main` yet, so the names below follow the folder layout we agreed earlier (`harness/data/sources/` holds what the agency has received).

**First, separate two jobs:**
1. **Delivery:** plain code that saves a new file into the sources folder, adds a line to `manifest.jsonl`, and records the event. No AI involved. In a real system this is the Gmail, Slack or tl;dv connector.
2. **Analysis:** the AI's staged workflow (what changed → questions → answers → recheck → human review → ATS update → recruiter recalibration). It starts because a new item arrived, not because a script contains a prompt.

I recommend not putting the prompt inside the delivery script. With them separate, every stage leaves a file that rule 13 can check, and swapping in a real connector later touches only delivery.

**How new information arrives:**

| Option | How it works | Benefit | Cost |
|---|---|---|---|
| **A. Pre-written timeline (recommended)** | Each role's future events are written in advance in `harness/scenarios/<client>/timeline/`: `01-jd.md`, `02-kickoff-transcript.md`, `03-expansion-news.md`… A **"client sent an update"** button in the UI (or `pnpm harness deliver --next`) moves the next one into `data/sources/` and starts the analysis. | Repeatable, and each event has your reviewed "intended reading", so we can test whether the AI caught the right change at the right severity. Demos are the same every time. | Only covers what we write. |
| **B. Recruiter pastes or uploads** | An "add client update" box in the UI: paste an email, notes or a transcript, then pick the channel and date. | It's what a recruiter really does today, and it shows how unfamiliar input is handled. | No answer key, so nothing to test against. |
| **C. AI-generated random change** | A script asks the model to invent a plausible client update. | Variety, stress testing. | No answer key, results differ between runs, and the AI ends up grading its own invention. It works against rule 13 and your reviewed references. |

**Recommendation:** build **A** as the main flow and **B** as a second input. If you want **C**, add it later as a "stress test" clearly labelled as generated and excluded from the tests.

**Two details that matter:**
- **A simulated clock:** each delivery moves the scenario date forward, so the UI can say "as of 14 Oct, after kickoff" and the profile versions (v1 JD → v2 kickoff → v3 expansion) line up with real events.
- **No peeking ahead:** the AI's tools read only `data/sources/`, never `scenarios/`. Otherwise the AI could see future events before the client sends them. This becomes a tested guardrail.

**In the UI:** a timeline of what has arrived, with a "next update from the client" card or notification showing a short preview such as "email from the founder, 2 Nov". Pressing it delivers the update, and the stage checklist then fills in live as each file appears.
